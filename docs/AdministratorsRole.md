# Administrators

Group id `104`, stored as `[Administrators]` (created by `setup/PatchLibrary/Worker/Updates/Update_8_5_138.cs`), enum value `enum_IR.AdmistrativeRoles.Administrators`. The role is the system-wide one: an administrator passes every administrative-role check, and a set of operations (libraries, property sets, document types, other users' recycle bins, the licence, the cache, the role groups themselves) is reserved for administrators alone. It is a system group: it belongs to no library (DOMAINID 0), it can be neither renamed nor deleted (`UsergroupOperations.cs`, group ids up to `IRConstants.LastSystemUserGroupId` = 1000 are system groups), and its members, like those of the other five role groups, are changed by administrators only: for `IrAdminAction.UpdateGroupMembers` on a group id up to 1000 `IRSecurity.IsAllowed` adds no role, so only the administrator check at the top of `AccessAllowedforAdminFunctionsAsync` passes.

## How the role is checked

**Who is an administrator.** `ThreadVariables.IsAdministrator()` (`IRNET/ThreadVariables.cs`): the signed-in user is the `sysadmin` account (`IRConstants.SysAdminAccountId`, user id 4) or a member of group 104 (`UserOperations.IsAdministrator`, a `UsergroupMembersStore.IsMemberOfGroupAsync` read). The membership is read from the database at each call; nothing is cached in the session, so adding or removing a member takes effect on the member's next request. An anonymous caller (user id 0 or below) is never an administrator. When the check is about another user's account, `IRSecurity.IsAdministratorAccountAsync` applies the same definition to that user.

**Where it is checked.** Four places decide, and administrators pass all four:

1. The role matrix, `IRSecurity.AccessAllowedforAdminFunctionsAsync`: its first line returns success for an administrator, before the "administrator's account" guard, before `IsAllowed` (self, role groups, library managers) and before the task-redirection special case. So an administrator passes every `IrAdminAction`, including the two for which the matrix adds no role at all: `FlushApplicationCache` and `UpdateGroupMembers` on a role group.
2. Direct `IsAdministrator()` checks in IRNET and WebServices (the operations in the first table below). A refusal is `errorCode="4030"` with, in most places, "Only the system administrator can perform this operation" (`Messages.OnlySystemAdministratorCanPerformOperation`); UpdateApplicationLicense, RemoveAllSubscriptions and RestoreRecycleBinItem answer "Access denied." (`Messages.AccessDenied`).
3. The Search & Category Administrators check, `UserOperations.HasAdministrativeRoleAsync` (used only by `IRNET/SearchPages.cs`): the `sysadmin` account passes, and the membership test is on the role group **or** group 104.
4. The library-management and workflow-management checks, `SecurityFunctions.CheckDomainManagementAsync` and `CheckWorkflowManagementAsync` (`IRNET/ModuleSecurityFunctions.cs`): both return success for an administrator before looking at library managers or workflow supervisors.

**Where it is not checked.** The item-level permission check, `IRSecurity.AccessAllowedAsync` (the `IrAction` rights on documents and folders), has no administrator branch at all: it looks at library membership, the library policy, ownership, library-manager status, the access list and the user type. An administrator is treated like any other user there. See "What the role cannot do".

**Refusal from the matrix** (for a non-administrator): `4030`, "Access denied. This action is restricted to the following roles: The system administrator, ..." followed by the roles the action admits (`IRSecurity.IsAllowed`).

## Finding out whether the signed-in user has this role

- [GetGroupMembershipsOfUser](GetGroupMembershipsOfUser.md) with the caller's own name: `IrAdminAction.ListingGroupMembershipOfUser` allows the self action, so every signed-in user may ask about themselves; a `GroupID` of `104` in the answer means the caller is an administrator. The `sysadmin` account (user id 4) is an administrator whether or not it is listed in the group (`ThreadVariables.IsAdministrator`).
- [getApplicationParameters](getApplicationParameters.md): the extended block (INDEXCATALOG, SMTPSERVER, PWDMINLEN, `AuthenticationAuthorities` and the rest) is present only for an administrator (`WebAPI/SettingsWebServices.cs`), which makes the call a direct administrator test that also covers the `sysadmin` account.
- [GetLibrariesForAdministration](GetLibrariesForAdministration.md) answers every library for an administrator, but also for User Managers and Policy Managers (`UserOperations.GetLibraryListForAdministrationAsync`), so it does not single the role out.

## Notes

- **Administrative versus item rights.** The administrator bypass exists in the administrative checks only. Library membership, the access list and the library policy still decide what an administrator may do with a document or folder, and GetDomains lists only the libraries the administrator is a member of. A Control Panel page that works on content (not on settings, users, libraries or definitions) must not assume an administrator can open it. `DomainMembersStore.IsDomainMemberAsync` counts direct membership and membership through a global group that is a library member; being in `[Administrators]` is not, by itself, a membership of any library.
- **Who else counts as an administrator's account.** The guard in `AccessAllowedforAdminFunctionsAsync` and the transfer guard (`UserTakeOverOperations.RunAsync`) use `IsAdministratorAccountAsync`: the `sysadmin` account or any member of group 104. Reading such an account (GetUser, GetUserStatistics, the activity lists) follows the ordinary rules; only changing it is reserved.
- **Transferring an administrator's memberships.** An administrator running [TransferUserGroupMemberships](TransferUserGroupMemberships.md) moves the role-group memberships too, `[Administrators]` included, so the to-user becomes an administrator. That is the intended administrator-only path; for anyone else the role groups stay behind.
- **UpdateApplicationLicense** refuses with the generic "Access denied." while the other administrator-only writers say "Only the system administrator can perform this operation". Same code (4030), different text.
- **GetManagedDomainsByUser** for another user is no longer administrators only: `UserServices.cs` lets whoever may look the user up read their managed libraries (administrators, User Managers, the user's library managers, co-workers).
- **Library lookup by name** has the administrator bypass since commit 61e1fb36 (`DomainOperations.MayReachAsync`, shared by the by-name and by-id lookups).
- **Not an ISrv operation:** the REST controller `IRWebCore/Controllers/PortalsController.cs` has `api/Portals/UpdatePortalSecurity`, administrators only (HTTP 401 "Access denied." otherwise).
- **The `sysadmin` user name** may be changed; the reserved names SYSADMIN, ADMINISTRATOR and SYSTEM are refused for every other account (`IrGeneral.IsValidFirstLastAndUserName`).
